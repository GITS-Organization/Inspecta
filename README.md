# Inspecta .NET API

ASP.NET Core 8 REST API for Inspecta. This repository contains the backend only; web or mobile clients consume the API over HTTP.

## API documentation

- Swagger UI: `/swagger`
- OpenAPI JSON: `/swagger/v1/swagger.json`
- Health check: `/health`

Swagger is enabled by default in every environment so a separately hosted frontend and API consumers can discover the contract. Set `Swagger__Enabled=false` to disable it. Authenticated endpoints use JWT bearer tokens; use **Authorize** in Swagger UI and paste an access token.

In Swagger the whole request and quotation workflow is one section, **Requests & Quotations**, listed first. Its endpoints are in the order a coordinator uses them (`Step 1 · List requests` … `Step 12 · Reject`), each with a short "when / how / next" guide, followed by the rarely needed extras. The titles and guides live in `Inspecta.Api/OpenApi/WorkflowDocs.cs`; when a workflow endpoint is added, add its step there. The legacy quotation drafts are listed last and labelled. The Certificates, PDF diagnostics and email test endpoints are hidden from Swagger (`ApiExplorerSettings(IgnoreApi = true)`) but still work; remove the attribute from their controllers to show them again.

It saves the generated body as the email preview and stores the reported machine issue on the request item. Coordinator IMAP mailboxes use a separate parser and create quotation drafts through the background sync workflow below.

### Coordinator email-to-request workflow

- When a Technical Manager creates a Coordinator using `POST /api/v1/manager/team`, include `emailConfig` with `imapServer`, `imapPort`, `emailUsername`, `password`, and `useSsl`. IMAP configuration is required for Coordinators and must not be sent for Inspectors. Passwords are encrypted with AES-GCM before being saved and are never returned by the API.
- Set `IMAP_ENCRYPTION_KEY` in Render as a stable Base64-encoded key containing exactly 32 random bytes. Configure the same value in `.env` for Docker deployments, or in user secrets for local development. Generate one with PowerShell:

  ```powershell
  $key = New-Object byte[] 32
  [System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($key)
  [Convert]::ToBase64String($key)
  ```

- Keep the same key across deployments and backups. If it is lost or changed, existing IMAP passwords cannot be decrypted; rotate mail passwords and reconfigure each Coordinator before replacing the key.
- Update mailbox settings through `PUT /api/v1/manager/team/{coordinatorId}/email-config`. Admins must add `?managerId={managerId}`. The API requires TLS: `useSsl=true` uses implicit TLS and `useSsl=false` requires STARTTLS.
- **Sending uses the same mailbox.** Quotation emails go out through the Coordinator's own mailbox with the same username and password as IMAP. The outgoing server defaults to the IMAP host with `imap` replaced by `smtp` (`imap.gmail.com` becomes `smtp.gmail.com`, `imap-mail.outlook.com` becomes `smtp-mail.outlook.com`) on port 587 with STARTTLS. If the provider differs, add `smtpServer`, `smtpPort` and `smtpUseSsl` (`true` for implicit TLS, usually port 465) to `emailConfig`. Like IMAP, the SMTP host must resolve to public addresses and the connection must use TLS. Providers such as Gmail need an app password with SMTP allowed. The message `From` is the mailbox username when it is an email address, otherwise the Coordinator's account email. If the mail server never answers, the send now fails after about 20 seconds with `502` and the text "The mail server did not answer": the hosting platform may block outgoing mail ports (Render blocks SMTP ports 25, 465 and 587 on free instances), so use a paid instance or an SMTP provider that offers another port such as 2525. **Emailing is currently switched off for testing** (`QuoteDelivery:Enabled` is `false` in `appsettings.json`, or set the environment variable `QuoteDelivery__Enabled`): Send and Accept still change the quotation and request state, but no email is sent and `emails` stays empty. Set it to `true` to send again; no code change is needed.
- `EmailSyncBackgroundService` checks every mailbox every 120 seconds by default (`EmailSync__IntervalSeconds` may be configured from 10 to 3600; `render.yaml` sets 15 for testing, raise it for production because every cycle opens a connection to each mailbox and some providers rate-limit logins). It opens the INBOX read-only (nothing in the mailbox is changed or marked read) and keeps a UID cursor per Coordinator. **Only mail that arrives after the mailbox was configured is imported**: the first sync just records where the mailbox stands, so existing mail is never turned into requests. Changing the IMAP server, port or username starts again from that moment; changing only the password keeps the cursor. A unique coordinator/UIDVALIDITY/UID constraint on `RequestEmails` prevents duplicates after a retry, and a message that fails to import is logged and retried next cycle (up to 5 attempts) without blocking the messages after it or other mailboxes.
- Each message becomes an `InspectionRequest` (`source: email`, `status: request_received`) owned by the Coordinator whose mailbox received it (`coordinatorId`) and by that Coordinator's Technical Manager team (`managerId`); both come from the mailbox configuration, never from the email. No quote or quotation draft is created.
- **Client senders and "maybe".** Each team keeps a list of client sender addresses or domains (`/api/v1/client-mail-rules`). Mail from a listed sender becomes a real request (`triage: request`) and, when the sender is linked to a client, is attached to that client (`clientId`, `clientName`). Mail from anyone else is kept as a `triage: maybe` email: it is not part of the request list, cannot be edited or moved through the workflow, and is deleted automatically 7 days after it arrived (`maybeExpiresAt` shows when). The owning Coordinator can `POST /api/v1/requests/{requestId}/confirm` to make it a real request, or `DELETE /api/v1/requests/{requestId}` to remove it right away (only maybe emails can be deleted this way). The sender address is read from the email header and can be spoofed, so a rule only decides where a message starts; the Coordinator still reviews every request.
- Client sender rules: `GET /api/v1/client-mail-rules`, `POST /api/v1/client-mail-rules` (`pattern` is an address such as `buyer@alnoor.com` or a domain such as `alnoor.com`; optional `clientId` of a client of the same team) and `DELETE /api/v1/client-mail-rules/{ruleId}`. Admin, Technical Manager and Coordinator can manage them; the list belongs to the Technical Manager team of the caller. Admin passes `managerId` (query for list, body for create). A domain rule matches exactly that domain, an address rule beats a domain rule, and rules apply to mail received after they are saved.
- `clientName`, `location` and `items` start empty (`clientName` is filled when the sender is linked to a client). `missingFields` on the request lists what is still needed (`clientName`, `location`, `items`); a request cannot move to `quote_draft` until it is empty. Manual requests keep their existing strict creation rules.
- The original message is stored in `RequestEmails` and returned by `GET /api/v1/requests/{requestId}/email`: sender and display name, To/CC/BCC/Reply-To, subject, Message-ID/In-Reply-To/References, sent date, plain-text and HTML bodies, and attachment names/types/sizes. Attachment content is not stored. `htmlBody` is untrusted sender content: sanitize it or render `textBody`. The request itself carries `emailFrom`, `emailFromName`, `emailPreview` (first 300 characters, single line) and `receivedAt` for list and detail screens.
- The owning Coordinator saves the request screen with one call, `PUT /api/v1/requests/{requestId}`: `clientId`, `clientName`, `location`, `preferredDate`, `accessNotes` and, optionally, the whole equipment list in `items` (`name`, `quantity`, `type`, `capacity`, `serialNumber`, `location` for the equipment location, `issueDescription`). Everything is validated first and saved in a single transaction, so either all of it is saved or none of it. `items` is a full replacement: an item with the `id` of an item of this request is updated, an item without an `id`, or with an `id` this request does not know (an id the app made itself is kept), is added, and existing items that are not listed are removed (an empty list removes all of them). Leave `items` out to keep the items untouched. Send the `updatedAt` you read as `expectedUpdatedAt` to get `409` (`request_changed`) instead of overwriting changes made in the meantime. The response is the updated request with the ids of every item, which the quotation prices need. Single items can still be changed with `POST|PUT|DELETE /api/v1/requests/{requestId}/items[/{itemId}]`. Editing is allowed only while the request is `request_received` or `quote_draft`; afterwards the API answers `409`. Linking a `clientId` requires a client of the same team.
- **Machines are registered automatically.** When the request is saved (also when a single item is added or edited), every item that is not linked to a machine record yet is registered in the machine catalog under the request client, and the item is linked to it (`equipmentId` in the response). A machine that already exists for that client (same name, serial number and capacity, ignoring case) is linked instead of duplicated, and the same machine twice in one save shares one record. If the request has no client, the team client with the same name (ignoring case) is used, or a new client is created from the typed `clientName` (location from the request) and linked to the request (`clientId`). Without a client name nothing is registered and the request still saves. The request, the new client and the new machines are written in one transaction. Typos in a typed client name therefore create a separate client record, so fix the name before saving or link the right client with `clientId`.
- **One save for the whole screen.** `PUT /api/v1/requests/{requestId}` saves the request screen and, as soon as the request is complete (client name, location and at least one item), opens the quotation in the same transaction: its items are copied from the saved items with empty prices (status `open`), the request moves to `quote_draft`, and the response is the request with a `quotation` (id, items, `missingPrices`, notes, proposal number) ready for the prices. The request then **leaves the request list** and is worked on in `GET /api/v1/quotations` (step 5) and `GET /requests/{requestId}/quotes/{quoteId}` (step 6). If a draft already exists, saving again refreshes it from the items and keeps the prices already entered, instead of creating a second one. While the request is not complete yet, the call is just a save (`quotation` is empty). `"prepareQuotation": false` always only saves; `"prepareQuotation": true` refuses an incomplete request with `409 request_incomplete` naming the missing fields and saves nothing. After a quotation was sent the request can no longer be edited (`409`), and a counter offer still uses `POST .../quotes`.
- Visibility: a Coordinator sees the manual requests of their team and only the email requests (real and maybe) that arrived in their own mailbox; other Coordinators' email requests answer `404`, including on transitions. A Technical Manager sees their whole team and an Admin sees every team (`GET /api/v1/requests?managerId=` narrows it). Only the owning Coordinator can edit, confirm or delete an email request; managers and admins have read access. Team scope comes from the JWT tenant claim and the data-layer tenant filter, not from request bodies.
- Listing: `GET /api/v1/requests` returns real requests by default, newest first, one page at a time (`page`, `pageSize` default 50, max 100). Requests whose quotation is open (`quote_draft`, `quote_sent`, `client_countered`) are left out of the default list and of the `requests` count: they continue in `GET /api/v1/quotations`, and an explicit `status=` still returns them. Query `triage=maybe` for the maybe tab, `status=quote_draft` (any workflow status) to filter, and `q=` to search client, location, subject and sender. `GET /api/v1/requests/summary` returns the tab counts (`requests`, `maybe`) and the number of real requests per status, within what the caller can see.
- Backlog cleanup (Admin only): `POST /api/v1/admin/email-backlog/cleanup` with `createdBefore`, optional `managerId` and `dryRun` (default `true`) permanently deletes email requests imported before that time that nobody started working on (still `request_received`, with no client, location, items or inspector). Run it once with the default dry run to see the count, then with `"dryRun": false`. Requests a Coordinator edited are never touched.
- Quotation drafts from the earlier workflow stay in the database and the `/quotation-drafts` endpoints still read and update them, but no new drafts are created. A message that was already imported as a draft is not imported again as a request.
- Not part of this stage: quote revisions, SMTP sending, PDF generation, and matching client replies to sent quotes. A reply that arrives now is imported as a new request.

### Quotations

- A quotation has three statuses: `open`, `accepted` and `rejected`. An open quotation is still being prepared while `sentAt` is empty, and waits for the client once `sentAt` is set. `canEdit` tells the UI whether the draft can still be changed. A sent revision replaced by a counter offer keeps its status and gets `supersededAt`.
- **My quotations:** `GET /api/v1/quotations` lists the quotations the caller can see across all requests, newest activity first, so a coordinator can pick one and start working on it. `stage=draft` (still being prepared), `sent` (waiting for the client), `accepted` or `rejected` filters them, `q=` searches client, quotation number and location, and `page`/`pageSize` page them (default 50, max 100). Only the latest revision of each request is returned unless `includeSuperseded=true`; Admin may narrow to a team with `managerId`. Visibility follows the requests: a coordinator sees the quotations of their own email requests and of the team's manual requests, managers see their team, and an inspector only gets the accepted quotations of the jobs assigned to them, **without prices** (`amountPiastres` is empty). Each row has `id`, `requestId`, `stage`, `requestStatus`, client, location, total, `totalUnits`, `missingPrices` (count), `canEdit` (true for a draft the caller may price and send) and the dates. To work on one, open it with `GET /requests/{requestId}/quotes/{id}` and save with `PUT` there.
- **Quotation queue (after acceptance).** Accepting a quotation (`POST .../accept`, or the client's answer recorded with `.../decision`) leaves the request `unassigned`; the quotation stays `accepted` and now lives in one of three queues, each row carrying `queue` (`unassigned`, `assigned`, `certify`): one endpoint, `GET /api/v1/quotation-queue?status=...`, where `status` is `unassigned` (waiting for an inspector), `assigned` (given to an inspector, `assigned`/`task_accepted`/`in_progress`) or `certify` (`certificate_submitted` onwards); without `status` it returns all of them. It takes `q`, `page`/`pageSize`, and `managerId` (Admin) or `inspectorId` (assigned and certify) filters, and follow the same visibility as `GET /quotations`.
- **Giving an accepted job to an inspector.** `GET /api/v1/inspectors` lists the team's active inspectors with `isOnLeave` and `activeJobs` (unfinished jobs they already have), and `POST /api/v1/requests/{requestId}/assignment` (`inspectorId`, `scheduledAt`, optional `note`) gives the whole job to one inspector; the request becomes `assigned`. The owning Coordinator, a manager or Admin may assign; an inspector of another team, or one on leave at that time, is refused. The Coordinator keeps full access and can call it again to hand the job to someone else until the inspector starts the work (`in_progress`). Rows show `inspectorName` and `scheduledAt`. The inspector signs in and gets only their own jobs from `GET /quotation-queue/assigned` (no prices; `GET /quotations` also still lists them), then `GET /requests/{requestId}` for the machines and client data.
- **Changing the inspection date.** `PUT /api/v1/quotation-queue/{requestId}/inspection-date` (`scheduledAt`, optional `note`) moves the date while the job is `assigned` or `task_accepted`; afterwards it answers `409`. The inspector of the job may do it and nothing else on the job (another inspector gets `404`); so may the owning Coordinator, a manager or Admin (a date inside the inspector's leave is refused for them). The change is written to the request history.
- **Inspection and certificates (per machine).** After assignment the inspector calls `POST /quotation-queue/{requestId}/start-inspection` (accepts the task and moves the job to `in_progress`) and gets the machines. For each machine: `GET .../machines/{requestItemId}` returns the whole form (header with client and standard(s), technical fields prefilled from the machine, the checklist, saved answers), `PUT` saves it as often as needed and `POST .../submit` sends it to the technical manager. The form depends on the machine's name, not its type or standard: `Certificates/Templates` holds 15 templates (a standard one plus 14 with a checklist) and a catalogue of the 58 known machines; a name the catalogue does not know gets the standard template. Submitting needs the examination and next-examination dates, the questionnaire, every checklist row answered (`yes`, `no`, `na`; a `no` needs a note, and a `no` or a danger answer also needs the defect description and the conclusion) and answers `409 certificate_incomplete` listing what is missing. When every machine of the job is submitted it becomes `certificate_submitted` and shows for the technical manager in `GET /quotation-queue?status=certify` (each row has `certificates`: total, submitted, approved, delivered). The technical manager approves each machine (`.../approve`: number `CRT-{year}-{code}` and verification code are generated, the machine's last/next inspection dates are updated; the QR code is added later) or returns it with a note (`.../return`). When every machine is approved the job is `certificate_approved` and the coordinator downloads the PDFs (`.../pdf`, marked DRAFT until approved) and calls `POST /quotation-queue/{requestId}/deliver-to-client`, which marks the certificates delivered and the job `sent_to_client`. To keep the app simple the answers already say what the current user can do: `canStartInspection` and `canDeliver` on the job, `canEdit` and `canReview` on each machine, and on the opened machine `readyToSubmit` plus `missing` (what still stops a submit; a failed submit returns `409 certificate_incomplete` with the same entries in `problems`). Dates are plain `yyyy-MM-dd`, statuses are lowercase snake_case (`not_started`, `draft`, `submitted`, `returned`, `approved`, `delivered`). **Approval, QR and the client's archive.** Approving a machine (`.../approve`, optional body `{ "signature": "[[x,y,...]]", "rememberSignature": true }`) gives the certificate its number `CERT-{year}-{0001...}` (counted per team and year) and a 16-character verification code, draws the **final PDF once** (QR code, signature, company details) and files it under the client with its SHA-256. `GET .../pdf` then returns that stored file, and the client's certificates are listed with `GET /clients/{clientId}/certificates` and downloaded with `.../{certificateFileId}/pdf`. The QR holds `{Certificates:PublicBaseUrl}/verify/{code}` (default `https://api.gitsplatform.com`): a public page (`GET /verify/{code}`, JSON at `GET /api/v1/verify/{code}`, limited to 60 requests a minute per address) that says whether the certificate was issued by us (`valid`, `expired` after its next examination date, or not found) and shows only what is printed on it. An item can carry a `testType` (optional, set when it is created or updated like `inspectionStandard`) that fills the certificate's Test type; the inspector can change it there.
- **Handing the certificates to the client.** When every machine is approved the coordinator can `GET /quotation-queue/{requestId}/deliver-to-client/preview` (recipient, subject, suggested text, attachments), `GET .../certificates.zip`, and `POST .../deliver-to-client` with an optional `sentTo` and `message`. With **`CertificateDelivery:Enabled=true`** the certificates are also emailed as a reply to the original request (the sender of the original email first, then the client's certificates email), from the coordinator's mailbox, with every PDF attached (one ZIP above about 18 MB); a refused email answers `502` and changes nothing, and a repeat never sends two emails. While it is **off (the default)** nothing is emailed and nothing fails: the answer's `delivery.emailSent` is false with a note. Turn it on with the environment variable `CertificateDelivery__Enabled=true`, on a host that allows outgoing mail (see the SMTP note above).
- **Older certificate endpoints.** The older certificate endpoints under `/requests/{id}/certificates` (hidden from Swagger) still work for certificates created with the older TÜV form.
- **Status rename.** The request status `quote_accepted` is now `unassigned`; a migration converts the stored requests and history rows.
- `POST /api/v1/requests/{requestId}/quotes` opens a quotation (optional `validForDays`, default 14). It copies **every item of the request** (description, PR number, quantity) with an empty price, starts the notes with the standard notes and the contact with the sender name of the original email and moves the request to `quote_draft`, so the request must already have its client name, location and items. A linked client is **not** required. Only one unsent quotation can exist per request.
- **Counter offer:** calling the same endpoint while the request is `quote_sent` and the latest quotation is still open creates the next revision. It starts with the previous prices, scope, notes and message, bumps the number (`rev01` becomes `rev02`), marks the previous revision as superseded and moves the request back to `quote_draft`. Older revisions stay as history.
- `PUT /api/v1/requests/{requestId}/quotes/{quoteId}` saves the draft: `items` (every request item exactly once, each with `unitPricePiastres`, which may stay empty in a draft; 1 EGP = 100 piastres), `validForDays`, `scopeOfWork`, `notes`, `message`, `proposalNumber` and `contactName` (the "Attention" line of the PDF). The proposal number is the reference printed on the PDF and in the email (default `QT-2026-1A2B3C rev01`); it can be changed freely while the quotation is a draft. Missing, duplicated or unknown items are rejected with `400`, and an item added to the request afterwards must be priced too. The total is always calculated from the item prices. The response lists `missingPrices` and `totalUnits`. A sent quotation can no longer be edited.
- `GET .../quotes/{quoteId}/pdf` previews the quotation as a PDF (rough layout for now, see PDF generation). A draft previews as if issued today; a sent quotation keeps its dates.
- **Replying by email.** `POST .../send` (the offer or counter offer) and `POST .../accept` generate the PDF automatically and email it as a reply to the sender of the original request (the `Reply-To` address when the email had one, otherwise `From`), threaded with `In-Reply-To` and `References`, from the owning Coordinator's mailbox, with a short text body and the PDF attached. `send` needs every item priced and then marks the quotation as sent (the request becomes `quote_sent`). `accept` closes the quotation as `accepted` (the request becomes `unassigned`); on a draft it sends and accepts in one step, so every item needs a price. The status only changes after the mail server accepted the message: if sending fails the API answers `502` (`email_delivery_failed`), nothing changes and the call can simply be repeated. Every attempt is stored (`emails` on the quotation: kind, recipient, `pending`/`sent`/`failed`, attempts, last error) together with the exact message and PDF that were sent, and a retry reuses the same Message-ID, so one quotation never produces two emails of the same kind. Requests without a source email (manual requests) are only marked, nothing is sent.
- `POST /api/v1/requests/{requestId}/reject` (body `reason`, required) turns the request down from any stage before acceptance: a new request, a quotation being prepared, or a quotation already sent. The open quotation, if there is one, is closed as `rejected` (even if it was never sent), the request becomes `quote_rejected`, and **no email is sent**. A `maybe` email must be confirmed first, and an accepted request cannot be rejected. `POST .../quotes/{quoteId}/decision` still records an outcome for a sent quotation without an email (`accepted`, or `rejected` with a `note`), for example when the client answered by phone.
- `POST /api/v1/requests/{requestId}/transitions` only drives the work after acceptance (inspector steps, certificates). Quotation steps (`quote_draft`, `quote_sent`, `unassigned`, `quote_rejected`, and the unused client-countered and client-declined) answer `409 quote_flow`, and `assigned` answers `409 assignment_flow`, because moving them directly would leave the quotation, the email or the inspector out of step. Use the quotation endpoints, `reject` and `assignment` instead; coordinators have no use for transitions.
- Existing quotations are migrated: drafts, sent, countered, expired and superseded quotations become `open`; accepted and rejected stay as they are.

### Technical managers, subscriptions, and user lifecycle

- A Technical Manager account represents the company using Inspecta and owns its subscription. The subscription has an explicit `Active`, `Suspended`, or `Expired` status and an optional end date. An active subscription becomes effectively expired when its end date is reached.
- Admin provisions a Technical Manager account through `POST /api/v1/technical-managers`; the subscription defaults to one month and can be set to 1–120 months. Admin can later update its status or end date through `PUT /api/v1/technical-managers/{managerId}/subscription`.
- A suspended or expired manager subscription blocks the manager and all assigned team members from using the API. Team accounts are linked directly to their manager through `ManagerId`; `CreatedById` remains audit information.
- Access tokens contain the user ID and role; team-member tokens also contain manager and tenant IDs, while a Technical Manager token uses that manager's own ID as its tenant. The API checks these claims against the current account and assignment on every authenticated request.
- Client, request, equipment, quote, certificate, contact, request-item, and history queries are scoped to the current tenant. Admin has global access. Existing client/request records without an owner remain visible to Admin only and are intentionally not auto-assigned during migration. There is no API for assigning historical ownership; use an explicitly reviewed data migration or administrative database operation before granting team access to those records.
- When publishing this authorization change, apply the included migrations before or as part of the rollout. Existing access tokens without tenant claims will be rejected; users must refresh their token or sign in again.
- User delete routes perform soft deletes, recording `IsDeleted` and `DeletedAt` instead of removing records. Deleted users are excluded from normal lists; Admin can pass `includeDeleted=true` to the user list route to include them.
- Disabling a user's `IsActive` account is separate from deleting it. Admin can change user status with `PUT /api/v1/users/{userId}/status`; a Technical Manager can change the status of a member in their own team with `PUT /api/v1/manager/team/{userId}/status`.
- Clients expose `isCompany` to identify company clients and `hasContract` to indicate whether a contract is in place; both default to `false`.

### Clients and items (Configurations)

In Swagger these are the **Configurations** section, listed after the request workflow (`Setup 1 · Create a client` … `Setup 8 · Update an item`).

- **Who may change them:** creating, updating and archiving clients and items is limited to Technical managers and Admin (a Coordinator gets `403`); Coordinators can still list and open them, for example to pick a client in a request. Recording an inspection stays open to Coordinators.
- `POST /api/v1/clients` creates a client with its profile (`name`, `isCompany`, `hasContract`, `location`, `latitude`/`longitude`, `certificatesEmail`, `taxNumber`, `notes`) and its `contacts` (name, email, phone, one `isPrimary`). A manager creates it for their own team; Admin sends `managerId`.
- `PUT /api/v1/clients/{clientId}` updates the profile. `contacts` is optional: a contact with an `id` of the client is kept and edited, one without an `id` is added, one left out is removed, and leaving `contacts` out keeps them as they are.
- `POST /api/v1/equipment` registers an item for a client: `clientId` is required and the client must exist and not be archived, so every item belongs to exactly one client, and `PUT /api/v1/equipment/{equipmentId}` cannot move it to another one. Besides `name` it takes `itemType`, `category`, `manufacturer`, `model`, `serialNumber`, `capacity`, `locationInsideClientLocation`, `notes`, `labels`, `dates`, `checklist`, `attachments` and **`inspectionStandard`**, the standard the item is inspected against (for example `ASME B30.5`, up to 200 characters). On update, `inspectionStandard` is kept when left out, changed when sent and cleared when sent empty. `GET /api/v1/equipment?clientId=...` lists one client's items.
- Clients and items are also registered automatically when a request is saved with a new client name or new machines. Those items start without an inspection standard; set it with `PUT /equipment/{equipmentId}`.

## Local development

Requires the .NET 8 SDK. From the repository root, configure a signing key and first admin with user secrets:

```powershell
dotnet user-secrets init --project .\Inspecta.Api\Inspecta.Api.csproj
$randomBytes = New-Object byte[] 48
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($randomBytes)
dotnet user-secrets set "Jwt:SigningKey" ([Convert]::ToBase64String($randomBytes)) --project .\Inspecta.Api\Inspecta.Api.csproj
dotnet user-secrets set "ConnectionStrings:Inspecta" "Host=localhost;Database=inspecta;Username=postgres;Password=<local-password>" --project .\Inspecta.Api\Inspecta.Api.csproj
dotnet user-secrets set "BootstrapAdmin:Email" "admin@example.com" --project .\Inspecta.Api\Inspecta.Api.csproj
dotnet user-secrets set "BootstrapAdmin:FullName" "Inspecta Admin" --project .\Inspecta.Api\Inspecta.Api.csproj
dotnet user-secrets set "BootstrapAdmin:Password" "<strong-password>" --project .\Inspecta.Api\Inspecta.Api.csproj
$mailKeyBytes = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($mailKeyBytes)
dotnet user-secrets set "IMAP_ENCRYPTION_KEY" ([Convert]::ToBase64String($mailKeyBytes)) --project .\Inspecta.Api\Inspecta.Api.csproj
```

Passwords must be at least 12 characters and include uppercase, lowercase, numeric, and symbol characters. Never put credentials or signing keys in `appsettings.json`.

```powershell
dotnet build .\InspectaBackend.slnx
dotnet test .\InspectaBackend.slnx
$env:Jwt__SigningKey = "<at-least-32-random-bytes>"
dotnet run --project .\Inspecta.Api\Inspecta.Api.csproj
```

Run a local PostgreSQL instance before starting the API. Local connection strings belong in user secrets, not `appsettings.json`. Local Swagger is available at `http://localhost:5238/swagger`; EF Core applies PostgreSQL migrations at startup.

## Linux deployment with Docker

Docker and Docker Compose are provided as a portable Linux deployment path; no hosting provider is assumed.

1. Copy `.env.example` to `.env`.
2. Set a unique `JWT_SIGNING_KEY` with at least 32 random UTF-8 bytes. Set the bootstrap admin values before the first start.
3. Start the API:

```bash
docker compose up --build -d
```

4. Verify `http://localhost:8080/health`, then open `http://localhost:8080/swagger`.
5. Put the API behind a TLS-enabled reverse proxy or the hosting platform's HTTPS ingress before exposing it publicly.

Set `API_PORT` to change the host port. Production secrets must be supplied by the server's secret manager or environment rather than committed `.env` files. Configure `AllowedHosts`, `Jwt__Issuer`, and `Jwt__Audience` for the deployed domain/client.
For a browser-based frontend on a different origin, set `CORS_ALLOWED_ORIGINS` to a comma-separated list of exact origins (scheme and host, such as `https://app.example.com`). Native clients and server-to-server consumers do not require CORS.

The API uses PostgreSQL. Set `INSPECTA_CONNECTION_STRING` to a PostgreSQL ADO.NET connection string before starting Docker Compose. Keep production credentials in the hosting provider's secret/environment settings, and use managed backups for important data.

dotnet build .\InspectaBackend.slnx --configuration Release

git diff --check

## Deploying to Render

The repository includes a [`render.yaml`](./render.yaml) Blueprint for the `backend` branch. Push the committed changes to GitHub first. In Render, choose **New > Blueprint**, connect this GitHub repository, select the `backend` branch, and review the Blueprint before deploying. It creates a Docker web service, configures `/health` as its health check, generates a JWT signing key, and asks for the PostgreSQL connection string and optional initial Admin email, full name, and password. If setting the bootstrap Admin, provide all three values together; the password must satisfy the API password policy.

Create a PostgreSQL database in Render in the same region as the web service. Copy its internal connection details into `ConnectionStrings__Inspecta` using the ADO.NET format `Host=<host>;Port=5432;Database=<database>;Username=<user>;Password=<password>;SSL Mode=Require`. Review Render's current database pricing and free-tier limits before creating it. The API creates/updates schema from its PostgreSQL migrations on startup; this starts with an empty database and does not copy data from the old SQLite file. The Render Blueprint creates the web service, not the database: create PostgreSQL in the same region first and then provide its internal connection string in the Blueprint settings. Review Render's current database pricing, free-tier limits, and database retention before creating it.

If creating the service manually instead of using the Blueprint, select the `backend` branch and Docker runtime with `Dockerfile` at the repository root. Set `ASPNETCORE_HTTP_PORTS=8080`, `PORT=8080`, `ConnectionStrings__Inspecta` to the PostgreSQL connection string, `Jwt__Issuer=Inspecta.Api`, `Jwt__Audience=Inspecta.Client`, and `Swagger__Enabled=true` if you want Swagger exposed. Set `Jwt__SigningKey` to a unique secret with at least 32 UTF-8 bytes. Bootstrap Admin settings are optional, but set `BootstrapAdmin__Email`, `BootstrapAdmin__FullName`, and `BootstrapAdmin__Password` together for the first deployment. Never commit these secrets. For Flutter Web, add `Cors__AllowedOriginsCsv` with the exact HTTPS origin of the deployed frontend; native Flutter apps do not need CORS.

After deployment, verify the Render service is healthy, check its logs for successful database migrations, call `/health`, and test login plus one protected endpoint. Confirm that tenant users see only their own assigned data and that Admin can see legacy unassigned records. Rotate or remove the bootstrap Admin password setting after the initial account is created, and keep a separate database backup/restore plan.

## PDF generation

Every PDF goes through `IPdfGenerator` (`Inspecta.Application/Pdf`), built on [QuestPDF](https://www.questpdf.com) in the infrastructure layer. Callers pass a plain model and get a `PdfFile` (bytes plus a safe file name), so the result can be returned from an endpoint, stored, or attached to an email.

To add a document:

1. Add a model record in `Inspecta.Application/Pdf/Models`.
2. Add a template in `Inspecta.Infrastructure/Pdf/Templates` that derives from `QuestPdfTemplate<TModel>` and implements `FileName`, `Title` and `ComposeContent` (override `ComposeHeader` and `ComposeFooter` when needed). A4 pages, margins, base font, metadata and page numbers come from the base class and `PdfTheme`.
3. Register it with `services.AddPdfTemplate<TModel, TTemplate>()` in `PdfServiceCollectionExtensions.AddPdfGeneration`.

The quotation template (`QuotationPdfTemplate`) reproduces the reference quotation of Integrity International for Inspection page by page (10 pages): illustrated cover, table of contents, cover letter, about us and vision, services, scope of work, budget with the notes, terms and conditions, and a thank-you page. A generated example is in `docs/samples/sample_quotation_generated.pdf`.

- **Where each value comes from.** Cover: client name and `Attention` (the quotation `contactName`, which defaults to the sender name of the original email and is editable in `PUT .../quotes/{id}`), subject (the distinct item types, for example "Mobile crane, Air receiver"), quotation number (`QT-year-code`, kept across revisions), issue date, valid-until date, and the preparer (the owning Coordinator's name, title "Coordinator"). Header: date, proposal number (editable) and page. Scope of work: the item types as a numbered list, then a table of PR number, description, quantity and unit of measure (`AU`), plus the scope points entered in the quotation. Budget: item description, `Per Visit`, cost per item, quantity and total in EGP, the total, and "14% VAT will be added". Notes: the quotation notes, which start as the standard notes and can be edited, followed by an automatic closing note with the validity in days. Terms: section 7.2 uses the validity in days.
- **Fixed company texts** (address, phones, about us, vision, services tables, terms, bank accounts) live in `DefaultCompanyProfile` and in `QuotationDefaults` (standard notes, VAT rate). They are the texts of the reference document; a `QuotationPdfModel.Company` profile replaces them when a per-company profile exists.
- **Images and font.** The cover illustration and the logo are embedded (`Pdf/Assets`). The cover image contains sample values that the template covers and rewrites. The reference uses the Inter font; drop `Inter-Regular.ttf`, `Inter-SemiBold.ttf` and `Inter-Bold.ttf` into `Inspecta.Infrastructure/Pdf/Fonts` (Inter is open source, SIL OFL) and rebuild, and every page uses it. Without the files QuestPDF's built-in Lato is used, which is close but a little lighter.

- **License:** QuestPDF is free under its Community license only for companies below its revenue limit (check the current terms at questpdf.com/license). Set `Pdf__QuestPdfLicense` to `Community` (default), `Professional` or `Enterprise` to match the license the company holds; any other value stops the API at startup.
- **Linux/Docker:** the runtime image installs `libfontconfig1`, `libfreetype6` and `fonts-dejavu-core`, which QuestPDF needs. QuestPDF's built-in font covers Latin text; DejaVu is the fallback for other scripts such as Arabic. Add a brand or Arabic font to the image before relying on specific typography.
- **Check a deployment:** an Admin can download a sample PDF from `GET /api/v1/admin/pdf/sample` to confirm generation works on the server.
